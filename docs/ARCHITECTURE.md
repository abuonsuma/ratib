# Ratib: Client Job Portal and ERP

Multi-tenant SaaS for printing, design and creative businesses in Ghana.
Version 0.1, architecture for approval before Phase 1 build.

---

## 1. Key decisions

| Decision | Choice | Why |
|---|---|---|
| Product model | Multi-tenant SaaS | Each business ("organisation") has its own data, branding, services, workflow and staff |
| Tenant isolation | Shared database, `org_id` on every table, enforced by Row Level Security | Cheapest to run, simple to maintain, safe when RLS is tested |
| Frontend and API | Next.js (App Router) + TypeScript | One codebase, server actions and route handlers for secure logic |
| UI | Tailwind CSS + shadcn/ui | Consistent, accessible, fast to build |
| Database and Auth | Supabase (PostgreSQL, Auth, Storage, Realtime) | Matches your spec; RLS built in |
| Payments | Paystack behind a gateway interface | Hubtel can be added later without touching business logic |
| Email | Resend (swappable) | Simple transactional email |
| Background jobs | Supabase Edge Functions + `pg_cron` + a `outbox` table | Reliable notifications without a separate server |
| Hosting | Vercel + Supabase | As specified |
| Tests | Vitest (unit), Playwright (end to end), pgTAP (RLS policies) | Auth, permissions, payments, workflows |

### Multi-tenancy rules
1. Every business table has `org_id uuid not null`.
2. A user belongs to one or more organisations through `org_members`, each with a role.
3. Clients are also members, with the role `client`, and see only rows where `customer.user_id = auth.uid()`.
4. Each organisation is reached by subdomain (`acme.ratib.app`) or a custom domain later. The tenant is resolved in middleware, never trusted from the client.
5. Platform-level owner (you) has a separate `platform_admins` table, outside all tenants.
6. Job numbers are unique **per organisation**: `JOB-2026-0001`, generated by a per-org counter row with a locked update (no gaps from race conditions).

## 2. System architecture

```
 Client browser / phone                 Staff browser
        |                                      |
        +------------- Next.js on Vercel ------+
        |   Middleware: tenant + session check |
        |   Server actions / route handlers    |
        |   (validation with Zod, price calc)  |
        +-------+------------------+-----------+
                |                  |
        Supabase Auth       Supabase Postgres  <---- RLS on every table
                |                  |
        Supabase Storage     Edge Functions + pg_cron
        (private buckets,          |
         signed URLs)       +------+--------+
                            |               |
                       Outbox worker    Paystack webhook
                       (email, in-app,  (signature check,
                        WhatsApp later)  idempotent)
```

Principles:
- **Server decides everything sensitive.** Prices, payment status, roles and job ownership are computed or checked on the server and in RLS, never taken from the browser.
- **Service-role key lives only on the server** (Vercel env vars). It is used in the webhook handler and workers, nowhere else.
- **Everything important writes an audit row** (database triggers for status and money tables, so nothing can skip it).

## 4. Database schema

All tables include `id uuid pk`, `org_id`, `created_at`, `updated_at` unless noted. Money is stored as integer pesewas (GHS x 100) to avoid rounding errors.

### Identity and access
| Table | Key columns |
|---|---|
| `organisations` | name, slug, logo_url, brand colours, currency, tax settings, status |
| `profiles` | user_id (auth.users), full_name, phone, avatar |
| `roles` | org_id, key (super_admin, manager, customer_service, designer, operator, accountant, delivery, client), name |
| `permissions` | key (e.g. `jobs.update_status`, `payments.record_manual`) |
| `role_permissions` | role_id, permission_id |
| `org_members` | org_id, user_id, role_id, status |
| `platform_admins` | user_id (outside tenants) |

### Customers and catalogue
| Table | Key columns |
|---|---|
| `customers` | user_id (nullable for walk-ins), name, email, phone, status, internal_notes |
| `service_categories` | name, slug, sort_order, active, workflow_id |
| `services` | category_id, name, description, form_schema (jsonb: fields this service asks for), active |
| `service_pricing` | service_id, pricing_type (fixed, per_unit, tiered), tiers (jsonb), size/material/finish options, urgent_surcharge_pct, design_fee |
| `workflows` | name |
| `workflow_stages` | workflow_id, status_key, label, order, requires_approval, requires_payment, notify_client |
| `workflow_transitions` | workflow_id, from_stage, to_stage, required_permission |

### Jobs
| Table | Key columns |
|---|---|
| `jobs` | job_ref, customer_id, service_id, title, status, estimated_completion, due_date, delivery_method, instructions, priority, assigned_to |
| `job_items` | job_id, description, quantity, specs (jsonb: size, orientation, colour, paper, finishing) |
| `job_files` | job_id, storage_path, filename, mime, size, kind (reference, design, deliverable), uploaded_by |
| `job_status_history` | job_id, from_status, to_status, changed_by, client_note, internal_note, created_at (insert only) |
| `job_assignments` | job_id, user_id, role_on_job, assigned_by |
| `job_messages` | job_id, sender_id, body, attachments, needs_response, read_by_client_at, read_by_staff_at |
| `job_counters` | org_id, year, last_number (locked update for job refs) |

### Money
| Table | Key columns |
|---|---|
| `quotations` | job_id, version, status (draft, sent, accepted, rejected, expired, superseded), subtotal, discount, tax, delivery, total, deposit_required, expires_at |
| `quotation_items` | quotation_id, description, quantity, unit_price, line_total |
| `invoices` | job_id, quotation_id, invoice_no, status, total, amount_paid, balance, issued_at, due_at |
| `invoice_items` | invoice_id, description, quantity, unit_price, line_total |
| `payments` | invoice_id, job_id, amount, method (momo, card, cash, bank), provider, provider_reference (unique), status (pending, success, failed, refunded), recorded_by (for manual) |
| `payment_events` | provider, event_id (unique), payload, signature_valid, processed_at (idempotency log) |

### Operations
| Table | Key columns |
|---|---|
| `deliveries` | job_id, method, driver_id, address, status, confirmed_at, confirmation_note |
| `notifications` | user_id, type, title, body, link, read_at |
| `notification_preferences` | user_id, channel, event_type, enabled |
| `outbox` | channel, recipient, template, payload, dedupe_key (unique), status, attempts |
| `audit_logs` | actor_id, action, entity, entity_id, before, after, ip, created_at (insert only) |
| `business_settings` | key, value (jsonb): payment rules, notification toggles, deposit % |

Future expansion (inventory, suppliers, expenses, payroll) adds new tables referencing `org_id`. No existing table needs to change.

### Row Level Security pattern
```sql
-- helper: is this user staff in this org with this permission?
create function has_perm(org uuid, perm text) returns boolean ...

-- staff see jobs in their org if they hold the permission
create policy staff_read_jobs on jobs for select
  using (has_perm(org_id, 'jobs.read'));

-- clients see only their own jobs
create policy client_read_own_jobs on jobs for select
  using (customer_id in (select id from customers where user_id = auth.uid()));
```
Writes to `payments.status`, `invoices.amount_paid`, and `jobs.status` are **not** allowed from the browser role at all. They go through server functions that check workflow rules.

## 5. Workflow engine

- Stages and transitions are **data**, configured per organisation and per service category (your 14 stages become the default template).
- A single server function `transitionJob(jobId, toStatus, note)` does the following in one database transaction:
  1. Checks the transition exists for this job's workflow.
  2. Checks the actor's permission for that transition.
  3. Checks gates: approval needed? payment condition met (deposit or full)?
  4. Updates the job, writes `job_status_history`, writes `audit_logs`, enqueues notifications in `outbox`.
- A job cannot reach a `requires_payment` stage unless a **verified** payment covers the configured deposit. This is enforced in the function and by a database check.

## 6. Payment flow (Paystack)

```
1. Client clicks Pay on an invoice.
2. Server creates a pending `payments` row with a unique reference and
   the amount taken FROM THE INVOICE (never from the browser).
3. Server calls Paystack "initialize" and returns the checkout URL.
4. Client pays (MoMo / card) on Paystack.
5. Browser returns to /portal/payments/return. This page ONLY shows
   "Checking your payment" and polls our own database. It never marks anything paid.
6. Paystack sends a webhook -> /api/webhooks/paystack
     a. Verify the HMAC signature. Reject if invalid.
     b. Insert into payment_events by event_id (unique). If duplicate, stop.
     c. Call Paystack "verify" server to server and compare amount,
        currency and reference with our pending row.
     d. In one transaction: mark payment success, update invoice
        amount_paid and balance, call transitionJob if the deposit is now met.
     e. Enqueue "payment confirmed" notification and receipt.
7. A scheduled reconciliation job re-verifies pending payments older than
   10 minutes, so missed webhooks never leave a job stuck.
```
Manual cash payments: only roles with `payments.record_manual`, with a mandatory note, and a full audit entry.

## 7. Notifications

- Any event writes rows to `outbox` (with a `dedupe_key` such as `job:123:status:ready`), so one event can never send twice.
- Edge Function worker reads the outbox every minute, checks the user's preferences, sends in-app (Realtime) and email, retries with backoff, marks sent or failed.
- WhatsApp Business is an extra channel in the same worker, switched off until you have approved templates.

## 8. Key user flows

**Client: submit a job**
Register -> verify email -> choose service -> guided form (fields come from the service's `form_schema`) -> upload files (type and size checked, stored privately) -> save draft or submit -> receives `JOB-2026-0001` and a confirmation -> sees timeline.

**Client: approve and pay**
Notification "Quotation ready" -> review items and totals -> accept, reject or ask a question -> pay deposit or full via Paystack -> status moves to Payment Confirmed only after webhook verification -> production starts.

**Staff: process a job**
Job arrives in queue -> reviewer opens it, prepares quotation (catalogue prices pre-fill, can be overridden with permission) -> sends -> after payment, assigns designer or operator -> moves through stages with client-visible notes -> quality check -> Ready for Collection -> client is notified -> collection or delivery is confirmed -> Completed.

**Accountant: reconcile**
Opens payments -> filters pending or failed -> sees gateway reference, invoice, job -> records a verified cash payment if needed (note required) -> exports CSV.

**Platform owner: onboard a business**
Creates organisation -> seeds default roles, workflow and catalogue -> invites the first Super Administrator -> tenant is live on its subdomain.

## 9. Security checklist
- RLS on every table, with pgTAP tests proving tenant A cannot read tenant B.
- Zod validation on every server action; prices recalculated on the server.
- Private storage buckets, short-lived signed URLs, MIME and size checks, filename sanitising.
- Rate limiting on login, password reset, file signing and webhook endpoints.
- Secrets only in environment variables; service-role key never in client bundles.
- Audit logs are insert-only (no update or delete policy).
- Backups: Supabase daily backups plus point-in-time recovery on the paid plan; restore procedure documented.
- Data protection: consent at registration, data export and deletion request process, aligned to Ghana's Data Protection Act, 2012 (Act 843). Have a Ghanaian lawyer confirm before launch.

## Addendum v0.2 (decisions after review)

**Target customer:** large print businesses, starting with a single-branch operation as the first real customer and design reference. The product stays multi-tenant.

| Topic | Decision |
|---|---|
| Branches | Not in Phase 1. Every table already has `org_id`, so a `branches` table and `branch_id` columns can be added later without rework. |
| Company clients | Phase 3: company accounts with several contacts, credit limits, payment terms, PO numbers, monthly statements. |
| Pricing | Phase 3: negotiated price lists per customer and manager approval above a quotation value. |
| Production | After Phase 3, shaped by a visit to the first customer: machines and work centres, routing, schedule board, capacity. |
| Job costing and inventory | Moved forward from "future" to sit right after Phase 3 (paper, ink and substrates stop production when they run out). |
| Payments | Paystack for deposits and card or Mobile Money. For large clients, bank transfer, cheque and invoice-on-credit reconciliation and aged receivables matter more. Each business connects its own Paystack account. |
| Tax | Tax lines are configurable. Confirm with an accountant or the Ghana Revenue Authority what a compliant tax invoice requires, including any e-invoicing rule, before building invoices. |
| Accounting | Export to the accounting software the customer already uses. |
| Isolation | Shared database plus Row Level Security by default. A dedicated database per tenant can be offered as a premium option. |

## Phase 1 as built (what differs from the plan above)

- **Fifteen stages**, not fourteen: "On hold" and "Cancelled" are separate off-track stages. The 14-stage list in the original brief merged them.
- **Job numbers are assigned on submit**, not on draft, so abandoned drafts never burn a number. Format `JOB-YYYY-NNNN`, sequential per business per year, race-safe through a locked counter row.
- **Clients cannot write to `jobs` directly.** Browsers only have SELECT. Creating, editing and submitting go through `save_job_draft`, `submit_job` and `delete_job_draft`, which re-validate everything and write history, audit and notification rows in the same transaction.
- **Clients never read the raw status history.** They read the `client_job_timeline` view, which hides internal notes and non-client-visible stages.
- **Sign-up always creates a plain client.** The business comes from the server's own host lookup, and the database trigger ignores any role in sign-up metadata.
- **Files** go browser to private storage in `{org_id}/{job_id}/…`; the server then records the file after validating type, size and path. Downloads use signed links that expire in 10 minutes.
- **Not in Phase 1:** staff dashboard and status changes (Phase 2), quotations, invoices, payments, outstanding balances (Phase 3), messaging and deliveries (Phase 4).

## Phase 2 as built (staff side)

**Who sees which jobs.** `jobs.read_all` (administrators, managers, customer service, accountants) sees every submitted job. Designers, operators and delivery staff hold only `jobs.read` and see jobs assigned to them. Staff never see a client's unsubmitted drafts. The same rule governs job items, files, history, internal notes and storage, because they all follow job visibility.

**One door for stage changes.** `transition_job()` is the only way a job changes stage. In one transaction it:
1. locks the job and re-checks permission and visibility;
2. refuses restricted stages unless the person holds the right (`payments.confirm`, `jobs.cancel`, `jobs.complete`; `jobs.reopen` to leave a finished job);
3. enforces the approval gate (leaving an approval stage forward needs a recorded approval);
4. enforces the payment gate (paid-only stages need payment cleared, switchable per business in Settings; **on by default**);
5. requires a client-facing reason for On Hold and Cancelled, and an internal note for a manual Payment Confirmed;
6. writes status history, audit log, an in-app alert and a queued email, each de-duplicated by an event key.

The screen asks the same rule through `job_next_options()`, so what is greyed out can never disagree with what is enforced. Stage rules are flags on the stages themselves (`requires_approval`, `requires_payment`, `required_permission`, `off_track`, `is_terminal`), so each business can change them. The separate `workflow_transitions` table from the first plan was not built: nothing needed per-pair rules yet, and it can be added without touching existing tables.

**Approval and payment until Phase 3.** Staff record client approval (`record_client_approval`) and confirm payment by moving a job to Payment Confirmed. Both write to `job_controls`, a staff-only table. In Phase 3 the Paystack webhook and the online approval button will write to the same two places, so the gates do not change.

**Email.** `outbox` is a queue with a unique `dedupe_key`. Workers claim rows with `FOR UPDATE SKIP LOCKED`, so two workers never take the same row. A row stuck in `sending` after a crash is reclaimed after 10 minutes, and parked as `failed` after five tries. The Resend request carries the dedupe key as an idempotency key. Only the server (service role) can touch the queue. Email links are forced onto the site's own address, and every value in an email is escaped.

**Not built yet:** automatic delay alerts, staff management screen, customer list, per-event email preferences, WhatsApp channel.
